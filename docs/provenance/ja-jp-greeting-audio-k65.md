# ja-JP greeting audio re-synthesis (K-65, finding #4)

Date: 2026-10-08. Host: OMP lab controller (linux x64). AI-generated,
**not human-reviewed**; the item `ja.lex.greeting.konnichiwa` stays
`review-needed` per ADR-0014. Nothing in this note claims a reviewed
pronunciation — it records measurements and one regenerated asset.

## Question from the owner report

The learner heard the first practice word as *"konichi ha"* instead of
*"konichi wa"*. Which input string fed to the pinned TTS actually yields
the `wa` mora for the topic-particle は, and does Kokoro's kana path get
it right?

| `konnnichiwa` (romaji) | 2.94 s | `K-ON-N-N-I-C-H-I-W-A` | — | — |

Kana ASR output is orthographically biased (is a written even
when /wa/ is heard), so a control set was synthesized: `こんわ` →
`こぅわら` (ASR can output わ outside greetings); nonsense `こんには`
→ `コンリーは` (base) / `こんにちは` (small/tiny) — showing whisper's
greeting bias and that the kana transcription channel alone cannot
settle ha-vs-wa.

### Acoustic mora-onset probe (`/tmp/k65-greeting/mora_probe.py`, pure Python)

Onset of the final mora (same vowel /a/) vs reference words: /h/ is
aspirated (high zero-crossing rate, low RMS), /w/ is sonorant.

| file | onset RMS | onset ZCR | matches |
| --- | --- | --- | --- |
| `はなし` (ha-) reference | 694 | 0.636 | /h/ |
| `わたし` (wa-) reference | 3103 | 0.038 | /w/ |
| `こんにちは` final mora | 1976 | 0.029 | **/w/** |
| `こんにちは。` final mora | 1863 | 0.036 | **/w/** |
| `こんには` (nonsense control) final mora | 2091 | 0.029 | /w/ (engine normalizes even misspelled は to wa) |
| `きょうは` (particle は) final mora | 1452 | 0.026 | **/w/** |

### Conclusions (v1_0 payload)

* The **kana form `こんにちは` is the correct input**: Kokoro's kana path
  produces the `wa` mora, including the particle は in `きょうは`, and
  even normalizes a deliberately misspelled `こんには` to wa.
* **Romaji input is unusable**: espeak spells the letters out
  ("K-ON-N-I-C-H-I-W-A"), ~2× the duration. This rules out the romaji
  `reading` scaffold as any TTS input on this engine.
* **Kanji input is unreliable**: `今日は` came out 0.44 s / garbled
  ("はぁ"). Do not feed kanji surfaces.
* The owner's *konichi ha* therefore cannot come from this engine fed
  the kana reading; pack-side audio is safe once generated from the
  declared kana reading. The live on-demand path (desktop crate, not
  owned by this change) is the remaining suspect.

  `validate` reports 0 errors / 0 warnings (the manifest row plus an absent
  `.wav` is a `media_missing` **error** while other assets are present, which is
  how this re-run was forced rather than skipped).
* Round-trip transcription on this host (whisper.cpp, `ggml-small.bin`,
  `-l ja`): the new asset → `こんにちは`; the pre-existing
  `ja.sent.greet-day.wav` (synthesized from the kanji surface) → `こんにちは`.
* Honest limit on the local check: ASR kana output is orthographically biased,
  and my own frame-level onset probe failed to separate the reference onsets
  (`はなし` ZCR 0.083 vs `わたし` 0.066, 10 ms frames — the segmentation swamps
  the contrast). It therefore proves nothing about the mora. The *wa* finding
  rests on the acoustic probe recorded above on the other host, not on this one.

## Independent reproduction (lab controller, same day)

The same single-id regeneration was run on a second machine to prove the fix is
not host-specific. Toolchain note: the multi-lang Kokoro bundle lives in the
**sherpa-onnx** `tts-models` releases (`kokoro-multi-lang-v1_1.tar.bz2`, tarball
sha256 `a3f4c73d043860e3fd2e5b06f36795eb81de0fc8e8de6df703245edddd87dbad`); the
kokoro-onnx releases carry no multi-lang package. The bundle's `model.onnx`
sha256 is `acc4adc1…` — identical to the `model_sha256` the other 693 rows pin.

* That run produced `sha256 204bdc43f5241b54813e7bc4ff7e8ce1cad88d9beb6f64f5bbd4a3938f3fc6dd`,
  73,088 B, 1.522 s, fed `こんにちは` from `readings(script)`. It is **not** the
  row this repo ships (that is the GamingPC `5893507c…` row above); the two
  differ only because synthesis is not byte-reproducible.
* Transcript of those bytes: `ggml-small -l ja` → `こんにちは。` (accept);
  `ggml-base` → `コンに期含!`; `ggml-tiny` → `コニチハン!`. The two weaker ASR
  models garble a 1.5 s clip; the acceptance transcript is always the small model.
* Live-fire of the new validator rule: rewriting that row's `text` back to
  `今日は` produced exactly one
  `error[media_text_not_declared_reading] … ja.lex.greeting.konnichiwa …
  declared reading(s) ["こんにちは"]`, and restoring it returned to 0 errors.
  The rule was never weakened to make the pack pass.
* Correction to the triage figure quoted in the tasking: "~419 lexicon entries
  without a script-tagged reading" matches no state of these files. All 3920
  lexicon entries declare a script-tagged reading; the real human-review gaps
  are the 8 contrast items listed in
  `languages/ja-JP/review/WORKLIST-2026-10-08.md`.
