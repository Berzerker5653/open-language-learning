## 2. Defect found while mapping: the kanji records cite the wrong source

Every one of the 84 kanji records declares `sources: ["jf-standard"]`. `jf-standard` is the
JF Standard framework, recorded as **reference-only, `UNLICENSED`,
`redistribution_allowed: false`** (`sources.jsonl:1`) — it is not a dictionary and nothing
in a kanji record comes from it. Meanwhile `licenses.jsonl:5` (`lic-kanji-dictionary`,
`path_glob: "kanji/*.jsonl"`, `source_id: "edrdg-jmdict"`) states the kanji data derives
from JMdict. The two records contradict each other in shipped data. The O-07 measurement
supports the JMdict side for readings and meanings (139/142 readings matched the mirror
verbatim; 72/84 records carry at least one verbatim gloss).

This is a **provenance misstatement, not a rights breach** — no JF Standard text was copied
— but shipped records that name a source they did not use are exactly what a downstream
user relies on. I have **not** patched it: changing a provenance claim is a content claim
that needs a human signature. Recommended change: `sources: ["edrdg-jmdict"]` on the 84
kanji records, with the band-framework reference kept only where it genuinely informed the
record (which for kanji entries appears to be nowhere).

## 3. The `radicals` field: unverified *and* sometimes wrong

From `state/evidence/O-07/jmdict-simplified-compare-2026-10-15.md`, over all 84 records:
27 radical sets exactly equal the KANJIDIC2/KRADFILE-derived `krad` lists, 16 are subsets,
2 supersets, 18 partial, and **21 are disjoint**. The classical indexing radical is present
in 60 pack lists and absent from 24. So the field is not merely unsourced: for a fifth of
the records it disagrees with the standard decomposition, and the UI shows it
(`apps/desktop/src/App.tsx:3070` renders `kanjiActive.radicals.join(" + ")` under the
character drill). `licenses.jsonl:5` already flags it honestly — "kanji `radicals`
provenance is an open question, O-07" — which is why shipping 0.4.1 unchanged is not a
silence, but it is not a fix either.

## 4. Does O-07 change the proposed 0.4.1 archive? Yes, if we act

- Acting on radicals changes `kanji/entries.jsonl` and `kanji/a2-topics.jsonl` → different
  member hashes → a different archive sha256. The candidate shas in
  `state/evidence/RC-0.4.1-2026-10-15/NOTES.md` are therefore only final **after** this
  decision is made.
- Not acting leaves the archive exactly as measured (0.4.1 = 0.4.0 + the 18 new audio
  members + the six metadata/text changes already accounted for), and O-07 becomes a
  0.4.2 content item with the uncertainty already declared in the pack's licence record.

That is the sequencing consequence the owner asked for: **O-07 must be decided before the
0.4.1 archive is frozen** if the radical problem is to be fixed in 0.4.1; otherwise it
delays nothing.

## 5. Proposed patch (prepared and verified, deliberately unapplied)

`state/evidence/O-07/patch-drop-unverified-radicals.patch` — 4 files, 228 lines:

1. `languages/ja-JP/kanji/entries.jsonl`, `kanji/a2-topics.jsonl` — remove `radicals` from
   all 84 records (84 lines changed, no other field touched).
2. `schemas/v0.2/kanji.schema.json:8` — drop `"radicals"` from `required`. **Required
   step, not optional:** with the data change alone the pack fails `validate`/`lint`/`test`
   with 84 `error[schema] … "radicals" is a required property`. The schema also sets
   `additionalProperties: false`, so there is no way to keep the field and mark it
   `unverified` in place. Relaxing a `required` list is backward compatible for existing
   packs; whether to do it inside `v0.2` or publish `v0.3` is an owner decision about the
   public schema contract (AGENTS.md requires a migration path for pack formats).
3. `apps/desktop/src/App.tsx:3068-3082` — render the radical/mnemonic line only when there
   is something to render; the Rust loader already tolerates a missing list
   (`str_array("radicals")` → `unwrap_or_default()` at `lib.rs:1105-1119`), and the record
   filter does not require radicals.
4. Not included, by design: the `lic-kanji-dictionary` wording, the per-record `sources`
   correction, and any re-sourcing. Those are claims, and claims are yours.

## 6. Recommendation

1. **Best fix if the learner-facing feature is worth keeping (verified, §5b):** re-source
   `radicals` from **KRADFILE** — the pack `sources.jsonl` record is `kradfile` (EDRDG,
   CC BY-SA 4.0), not `edrdg-kanjidic2`: the replacement lists come from the KRADFILE
   component data (as converted by jmdict-simplified 3.6.2), and KANJIDIC2 itself is used by
   nothing in the pack, so naming it would repeat the very misstatement this ticket is about.
   Keeps the drill's decomposition line and makes it sourced; costs mnemonic drift (§5b) and
   two licence duties that are still open work (§5b). Changes the archive, so it must precede
   the freeze if chosen.
2. **Honest fallback (verified patch above):** drop the field and relax the schema. Removes
   a claim the repository cannot support. Costs the decomposition hint in the drill UI.
3. **Not recommended:** keep the values as they are and only re-word the licence note. 21
   disjoint radical sets are wrong content, not just unsourced content.
4. Either way, fix the `sources: ["jf-standard"]` misstatement on the 84 kanji records —
   that one is independent of the radicals decision and independent of 0.4.1 timing only in
   the sense that it too changes the archive.

## 7. What stays explicit

- The packs remain `experimental`; `--release-readiness` still reports 5 FAILs, and no
  amount of provenance bookkeeping clears that without a qualified human review record.
- The 0.4.1 candidate is a preparation artifact: no tag, no release assets, no catalogue
  edit, and the 18 tracked journey audio files stay in git until replacement distribution
  is published and verified (ADR-0032).
- `jf-standard`'s `redistribution_allowed: false` is a claim about our behaviour that no
  machine check enforces; the only real assurance is human review of the pack's text.
