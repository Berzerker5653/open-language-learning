# PACK-UPDATE-TIMING — measured 2026-10-17

First machine-measured evidence for what an installed user waits for when a
reference pack updates: HTTPS download, SHA-256 verification, and unpack/install
into the pack store, for the published 0.4.1 reference packs.

This is a single-run-class machine measurement, **not** the owner's hands-on
O-06 experience pass.

## Machine

- Host: Omarchy (OMP controller; same machine the measurement ran on)
- CPU: AMD Ryzen AI MAX+ 395 w/ Radeon 8060S, 32 logical CPUs (16 cores, SMT), single NUMA node
- RAM: 62 GiB total (26 GiB free at measurement time)
- Disk: NVMe SSD, KIOXIA-EXCERIA-BASIC 1.8T (`rota=0`), ext4 on LVM (`/dev/mapper/root`, 1.7T free)
- Network: direct, no proxy (no `*_proxy` env vars set); GitHub release assets
  served via Fastly CDN (remote 185.199.108.133 / 185.199.111.133), 1 redirect each

## Method

Real code path, not a reimplementation:

- Archives: the two rows of `catalog/packs.json` (`org.openlanguage.ja-jp.reference`
  0.4.1, `org.openlanguage.ru-ru.reference` 0.4.1), pinned `sha256` + `size_bytes`.
- Download: `curl --fail --location` to `tmp/pack-timing/` (curl `time_total`).
  The app's own fetcher is resumable `reqwest` with progress callbacks; curl
  measures transfer time only (see caveats).
- Verify + install: `crates/langpack/tests/perf_install.rs` (`#[ignore]`d), which
  calls the public `lts_langpack::archive` API — `hex_sha256` (identical to the
  desktop `install_pack_bytes_report` checksum step, `packs.rs:760`) and
  `archive::install` (the same entry `install_from_catalog_report` reaches via
  `install_with_cancel`, `archive.rs:248/260`). `install()` includes the entry
  safety scan, decompression, per-entry SHA-256 checks, staging writes,
  `Pack::load_dir` + `validate(Mode::Install)` (incl. media audit), and the
  atomic store rename.
- Build profile: `--release` (what an installed user runs).

Commands, run from the repo root (`cargo` 1.97.1 via rustup):

```
mkdir -p tmp/pack-timing
curl --fail --location --silent --show-error -o tmp/pack-timing/ja-jp-reference-0.4.1.lpk \
  -w 'time_total=%{time_total}s size=%{size_download} speed=%{speed_download}B/s' \
  'https://github.com/Berzerker5653/open-language-learning/releases/download/org.openlanguage.ja-jp.reference-0.4.1/ja-jp-reference-0.4.1.lpk'
curl --fail --location --silent --show-error -o tmp/pack-timing/ru-ru-reference-0.4.1.lpk \
  -w 'time_total=%{time_total}s size=%{size_download} speed=%{speed_download}B/s' \
  'https://github.com/Berzerker5653/open-language-learning/releases/download/org.openlanguage.ru-ru.reference-0.4.1/ru-ru-reference-0.4.1.lpk'
LTS_PERF_PACK_ARCHIVE=$PWD/tmp/pack-timing/ja-jp-reference-0.4.1.lpk \
LTS_PERF_STORE=$PWD/tmp/pack-timing/store-ja \
  cargo test --release -p lts-langpack --test perf_install -- --ignored --nocapture
# same for ru-ru-reference-0.4.1.lpk / store-ru; run twice per pack
```

The test itself deletes and recreates the store, so run 1's install is
fresh-store and run 2 starts fresh again; the "over-existing" number is the
same run's second `install()` over the version it just wrote (the
upgrade/replace path, `archive.rs:400-403`).

## Integrity: measured sha256 vs catalog pins

`sha256sum` of the downloaded archives matched `catalog/packs.json` exactly:

| pack | catalog sha256 | measured sha256 | match |
|---|---|---|---|
| ja-JP 0.4.1 (318,722,747 B) | `e697ee92f6602c3373ebe5910f0dfbee8e50edcb3e9a25b2890efba5a5964690` | same | yes |
| ru-RU 0.4.1 (318,489,935 B) | `9eb074fa8d59f508108bc0fa8c698e1ddbd7458648ee2d829edeb36fbcfc1d7a` | same | yes |

Sizes matched the pinned `size_bytes` exactly (asserted by the test).

## (a) HTTPS download — curl `time_total`, run 1 only (not repeated)

| pack | bytes | time | throughput |
|---|---|---|---|
| ja-JP | 318,722,747 | 4.412 s | 72.2 MB/s |
| ru-RU | 318,489,935 | 3.930 s | 81.0 MB/s |

## (b)-(d) verify + install, release build — every run

All four runs executed; nothing discarded.

| phase | ja-JP run 1 | ja-JP run 2 | ru-RU run 1 | ru-RU run 2 |
|---|---|---|---|---|
| archive read from disk (page cache) | 0.038 s | 0.039 s | 0.038 s | 0.039 s |
| (b) SHA-256 verify vs catalog pin | 0.127 s | 0.130 s | 0.129 s | 0.127 s |
| (c) `install()` fresh store | 1.448 s | 1.446 s | 1.371 s | 1.361 s |
| (d) `install()` over existing version | 1.501 s | 1.522 s | 1.421 s | 1.419 s |

Bytes/sec (per archive byte; extracted store is larger — 417 MB ja, 399 MB ru):

| phase | ja-JP | ru-RU |
|---|---|---|
| verify | 2.39 GB/s (2,387 MiB/s) run 1; 2.33 GB/s run 2 | 2.35 GB/s run 1; 2.40 GB/s run 2 |
| install (fresh) | 220 MB/s (210 MiB/s) run 1; 220 MB/s run 2 | 233 MB/s run 1; 234 MB/s run 2 |
| install (over existing) | 212 MB/s run 1; 209 MB/s run 2 | 224 MB/s run 1; 224 MB/s run 2 |

End-to-end on this machine, download through install (no app bookkeeping):
≈ 6.0 s (ja-JP run 1), ≈ 5.4 s (ru-RU run 1) — dominated by the transfer.

## Cache state (explicit)

- **Warm page cache for all (b)/(c)/(d) runs.** The 318 MB archives stayed in
  the 62 GiB RAM page cache after download; extracted-store writes were also
  still in page cache when `install()` returned (rename within one filesystem;
  writeback lands later). No cold-cache run was taken: dropping caches needs
  root and was not attempted. A cold-cache install on slow storage would be
  slower; on NVMe + this RAM the warm numbers match the app's actual flow,
  which holds the whole archive in memory (`install(bytes, store)`).
- Run 2 was also warm (run 1 just touched everything).
- Download (a) is by definition cold-network; run 2 did not re-download.

## Caveats

- **Single machine, small-N.** Four verify/install runs per pack, one download
  per pack. No repeat distribution, no contention, no other load recorded.
- **Download time is network-dependent and must not be quoted as an app
  performance claim.** ~72-81 MB/s reflects this host's path to GitHub's CDN
  on 2026-10-17; it is context for the total wait, not a property of LTS.
- curl timings use `time_total` (incl. TLS + 1 redirect); the desktop fetcher
  is a resumable `reqwest` loop with per-chunk progress callbacks and partial
  file handling, so its wall time may differ by connect overhead and buffering.
- Install here is single-threaded through inspect, safety scan, inflate,
  per-entry SHA-256, install-mode validation (incl. media audit of every
  declared wav), and rename — the number is the real user-perceived wait on
  this profile, but it will move with CPU, not just disk.
- The desktop install additionally pays `Store::record_installation` and
  `warm_pack` (parse-on-install, K-63-follow), which are outside
  `install()` and not timed here.
- This is machine evidence only. The acceptance owner's hands-on O-06 pass
  remains separate and unmet by this document.

## Reproduce

```
cargo test -p lts-langpack --test perf_install -- --ignored --nocapture   # with LTS_PERF_* set, see test header
```

Scratch (`tmp/pack-timing/`, ~1.4 GB) was deleted after measurement.
