# K-03 — READ-001 adaptive reader wired into practice

## What shipped
- `LexEntry` gained `romaji` (readings with `transliteration_system`), so
  romaji is pack data, not engine transliteration.
- `PracticeTask` gained `furigana`, `romaji`, `faded_by_mastery`; the plain
  `reading` field remains for non-Japanese packs.
- `reader_display` (lib.rs) delegates to `lts_activity::render_reading_display`
  with the derived per-item `ComprehensionReading` state and profile settings
  `romaji-mode` (auto/always/off) and `kana-literacy-established`.
- Scaffolds fade by mastery: furigana hides at `supported` reading state;
  kana romaji hides once kana literacy is established.
- Reveal: `practice_task`/`practice_submit` take `reveal_reading`; revealing a
  faded scaffold records support level 3 with the concrete action
  (`supplied-reading` / `romaji-reveal`); revealing an already-auto scaffold
  records no support. UI "Show reading" button refetches with reveal=true.
- Reader gating is Unicode-script based (`script_of`), never locale: the
  reader only asserts for Japanese-script surfaces, keeping the engine
  language-neutral while READ-001's canonical-form assert stays safe.

## Language-pack reuse
Fade thresholds come from `JA_ORTHOGRAPHY_POLICY.yaml` mirrored as
`HIDE_AT_STATE`; romaji/furigana availability is per-entry pack data. Packs
for other scripts supply `reading`/`romaji` fields and get the same fade and
reveal accounting through the same display path.

## Evidence
- Rust test `reader_fades_scaffolds_and_reveals_record_support`: watashi shows
  furigana+romaji; two ComprehensionReading successes (distinct prompt
  families) fade furigana (`faded_by_mastery`); reveal then records support 3
  + `supplied-reading`; first reveal against auto scaffolds records support 0;
  `kana-literacy-established` hides konnichiwa romaji.
- vitest: furigana-above-surface ordering + reveal-button-only-when-faded
  cases in `practice.test.tsx` (33 tests total).
- Xvfb desktop smoke passed after change.

## Note on test determinism
`evidence_for_profile` orders by `(occurred_at, event_id)` and event ids embed
subsecond counts, so same-second submits do not sort chronologically; the test
asserts existence of the support-3 event rather than "last event".

## Smoke build gotcha (fixed)
Manual `cargo build -p lts-desktop` debug binaries load `devUrl`
(`localhost:1420`), not the embedded `dist/` — the smoke handshake then
never fires and the webview shows a WebKit connection-error page. The
official `scripts/smoke-desktop.sh` avoids this via `tauri build --debug`
(which enables `tauri/custom-protocol`). `apps/desktop/src-tauri/Cargo.toml`
now exposes a `custom-protocol` feature so the manual path is
`cargo build -p lts-desktop --features custom-protocol`.
